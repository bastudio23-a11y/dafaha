# دفعة — تقرير نسخة الغرف الجماعية

## النطاق
هذه نسخة تطوير مستقلة عن الإنتاج. أُضيفت واجهة لإنشاء غرفة برمز عشوائي من 8 رموز، وانضمام الزائر باسم فقط كجمهور أو متحدٍّ، وروابط دعوة وموافقة المضيف على المتحدّين. بقيت تجربة الجولة والتصويت والنتائج ولوحة الترتيب من الواجهة الحالية.

## البنية والأمان
- Express على Render مسؤول عن حالة كل غرفة وتحديد الصلاحيات.
- المضيف يُحفظ اعتماده في Cookie عشوائي آمن (HttpOnly وSameSite=Lax، وSecure على HTTPS الإنتاجي).
- الجمهور يستطيع التصويت على جولته فقط، والمتحدّي ينتظر الموافقة؛ تغيير المراحل والإدارة والتصفير حكر على المضيف.
- تحديثات اللعبة فورية عبر Server-Sent Events وتُخصص لكل عضو؛ إجابات الجولات لا تُرسل للجمهور قبل النتائج، ولا تصل مهارة المنافس للمتحدّي الآخر.
- يوجد حدّ لطلبات إنشاء الغرف والانضمام والأوامر. رمز الغرفة وحده **لا يمنح صلاحيات المضيف**.
- تم إزالة واجهات API القديمة المشتركة التي لم تكن تتحقق من المضيف، واعتماد مصدر حالة واحد لكل غرفة.

## حدود النسخة الأولى
- **الغرف مؤقتة**: الحالة محفوظة في ذاكرة سيرفر Render فقط. ستختفي الغرف والنتائج عند إعادة التشغيل أو توقف السيرفر، وكذلك بعد 6 ساعات من عدم النشاط. لا تعتمد عليها بعدُ لمسابقات طويلة أو مهمة.
- لكل متصفح Cookie جلسة واحدة نشطة، وقد يحتاج المضيفون واللاعبون تجربة مستقلة أو ملف متصفح مختلف إذا استخدموا الجهاز نفسه.
- الحد المبدئي: 150 جلسة داخل الغرفة و300 غرفة في العملية. هذه حدود في الكود وليست ضمانًا لسعة الاستضافة المجانية.
- لا يوجد تسجيل حساب أو استعادة لصلاحية المضيف بعد فقدان Cookie أو إعادة تشغيل السيرفر.
- اللعب الجماعي يتطلب Render أو سيرفر Node متصلًا؛ نشر الملفات الثابتة فقط على GitHub Pages لا يشغل الغرف.
- سجل النقاط واللعب القديم على Firestore لا يُنقل إلى النسخة الجديدة تلقائيًا.

## حالة Firestore
ملف firestore.rules في فرع التطوير يتجه إلى المنع الافتراضي لأنه لم يعد يُعتمد على الكتابة المباشرة من العميل للعبة. **لم تُنشر هذه القواعد**. قبل النشر يجب التحقق من أن قاعدة Firebase المستهدفة تخص دفعة وحده، وعدم تطبيق المنع قبل تفعيل النسخة الجديدة على Render. قواعد الإنتاج الحالية منفصلة عن نسخة GitHub.

- TypeScript: npm run lint
- عزل الغرف وصلاحيات المضيف وانضمام الضيوف وإخفاء الإجابات: npm run test:rooms

## خطة إطلاق آمنة
1. اعتماد شكل الغرف وما إذا كانت مؤقتة الآن، أو إضافة تخزين دائم قبل الإطلاق.
2. فحص المشروع Firebase الحقيقي والتأكد من عدم مشاركة قاعدة البيانات مع مشروعات أخرى.
3. اختبار نسخة Staging لها رابط مستقل بموافقة المالك.
4. التأكد من عمل الغرف من جهازين وشبكتين مختلفتين ومن سلوك إعادة الاتصال والتوقيت.
5. مراجعة طلب الدمج، ثم نشر فرع main على Render **بعد موافقة صريحة**.
6. تطبيق قواعد Firebase المناسبة من خلال عملية منفصلة مع خطة استرجاع.
7. مراقبة سجل Render والأخطاء بعد الإطلاق.
